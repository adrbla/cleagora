# DEVS.md – Working with Claude & context files

## 1. What this is for

This project uses the **Nexus** — a lightweight set of context files (`CLAUDE.md`, `DEVS.md`, `context/*.md`) that give AI assistants and humans a shared, persistent view of the project: vision, decisions, backlog, and session history.

This project is set up so that:

- You can use AI (Claude Code, Cursor, Kiro, etc.) as a **pair programmer**.
- The project's **state and decisions** live in a small set of text files (`context/…`) that stay in sync with the work.
- As a developer, you **do not have to write documentation by hand**: the assistant drafts it, you just review.

The goal is that a Product Owner can open the repo at any time, load it into an AI coding assistant, and immediately understand:

- What happened recently.
- Which decisions were made.
- What's currently in the backlog.

***

## 2. The files that matter

You'll see these files in the repo:

- `CLAUDE.md`
  Instructions for the AI assistant when working on this project (role, stack, constraints, links to context files).

- `context/vision.md`
  High-level: why this project exists, for whom, main constraints.

- `context/journal.md`
  Narrative session log in **reverse chronological order** (newest entry first): what was done, what changed, risks and open questions.

- `context/decisions.md`
  Important architectural/product decisions extracted from the journal when they matter for future work.

- `context/backlog.md`
  Now/Next/Later list of tasks and ideas.

- `context/tech-stack.md`
  Languages, frameworks, tools, and coding conventions. Auto-generated by the assistant (by scanning the repo) and kept up to date — you review it, you don't write it.

`context/vision.md` also declares a **project stage** (Exploration → Foundation → MVP → Growth → Maintenance) that sets default expectations for rigor, testing, and documentation.

You are not expected to maintain these manually. Instead, you use the assistant to generate updates at the right times.

***

## 3. How it works in practice

### At the start of a dev session

1. Pull the latest changes.
2. Skim, in order:
   - `CLAUDE.md`
   - Last one or two entries in `context/journal.md`
   - Recent items in `context/decisions.md`
   - The "Now" section in `context/backlog.md`

3. Open your AI coding assistant in the **project root** and give it a first message.

   **If this is your very first session** on this project (tech-stack.md is still a placeholder):

   > "You're working in the cleagora repo. Read `CLAUDE.md`, then `context/vision.md`, `context/journal.md`, `context/decisions.md`, and `context/backlog.md`. This is your first session — follow the 'First session on this project' workflow in `CLAUDE.md`."

   **For subsequent sessions**:

   > "You're working in this repo. Read `CLAUDE.md`, then `context/vision.md`, `context/journal.md` (latest entry), `context/decisions.md`, and `context/backlog.md`.
   > Summarize the current state in a few bullets and propose 2–3 concrete tasks from the Now backlog for this session."

***

### During the session

Use the assistant as you normally would:

- Ask for help designing or implementing features.
- Get code suggestions, refactors, tests, etc.
- Discuss trade-offs before making bigger architecture or product decisions.

**Project-specific notes**:

- **Discourse**: we work primarily through Discourse's API, plugin system, and theme components. Avoid modifying Discourse core.
- **Pipeline**: the extraction/enrichment pipeline is Python-based. Keep it modular — extraction from Discourse, enrichment/metadata generation, and output formatting should be separate concerns.
- **Exploration stage**: we're validating the concept. Speed matters more than polish. But document your findings — what works, what doesn't, what surprised you.

***

### At the end of a session: "close the loop"

When you reach a meaningful stopping point, run a **meta-prompt** to update the context files.

Example prompt you can reuse:

> "We're wrapping up this dev session. Based on our conversation and the changes we made, do three things:
> 1) Prepend a new section at the top of `context/journal.md` (below the title) summarizing what we did, what changed, and any risks or open questions for the PO.
> 2) If we made any real decisions, add or update entries in `context/decisions.md` (date, context, decision, alternatives, consequences).
> 3) Update `context/backlog.md`: mark what's done in Now, and add or adjust Now/Next/Later tasks for follow-up work.
> 4) If there are open questions for someone not present (PO or another dev), add an 'Open questions' section to the journal entry, tagged by audience.
> Show me the exact edits you propose for each file so I can review."

Then:

- The assistant will draft the new sections / changes.
- You skim them, tweak if needed, and apply them (or let your tool apply them).

***

## 4. Guidelines and expectations

- **You are not the documentation writer.**
  Your job is to trigger the meta-prompt at the end of a session, check that the generated updates are roughly accurate, and commit them along with your code.

- **Be honest in the journal.**
  Include what you tried, what worked / didn't, unknowns or technical risks you want the PO to see.

- **Keep decisions meaningful.**
  Only record decisions that matter: API design, architecture, libraries, trade-offs that might be revisited later.

- **Let the backlog stay high-level.**
  Focus on features / work packages and follow-ups that the PO should be aware of.

***

## 5. Example end-of-day flow

1. You finish setting up the Discourse API extraction script and commit your changes.
2. You tell the assistant:

   > "We just built the initial Discourse API extraction — pulling topics and posts from a test instance. Draft updates for `context/journal.md`, `context/decisions.md`, and `context/backlog.md` as per the project workflow."

3. The assistant outputs:
   - A journal section describing what happened and open questions (e.g. "rate limiting on Discourse API needs investigation").
   - A decision entry (e.g. "we chose the Discourse API over direct DB access for extraction — alternatives considered…").
   - Backlog edits (mark "initial extraction" as done, add "enrichment pipeline" and "rate limit handling" tasks).

4. You review, adjust if something is wrong, and apply.

***

If anything in this workflow feels heavy or unclear in your day-to-day usage, please note it in a journal entry and/or tell the PO so we can adjust the prompts and expectations.
